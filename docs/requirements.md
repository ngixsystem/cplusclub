Ты — ведущий разработчик проекта. Создай работающий MVP веб-приложения для компании, обслуживающей компьютерные клубы. Требуется реализовать приложение в репозитории, запустить его в Docker и проверить основные сценарии.

Не ограничивайся планом, макетом или CRUD-заготовкой. Работай последовательно до выполнения критериев приёмки. Не обещай абсолютную надёжность: подтверждай качество тестами, измерениями и воспроизводимыми проверками.

## 1. Контекст бизнеса

Мы обслуживаем компьютерные клубы с бездисковой системой CCBoot и iCafeCloud.

В команде:
- Анвар — технический руководитель: серверы, сеть, образы, сложная диагностика.
- Выездной специалист — осмотр и чистка ПК, замена согласованных деталей, работа с заявками, фотоотчёты.

Каждый ПК должен проходить плановый осмотр раз в два календарных месяца. Чистка выполняется по состоянию и согласованному объёму.

Приложение должно объединить:
- клубы и оборудование;
- заявки и выполненные работы;
- график осмотров;
- мониторинг оборудования;
- контроль обновлений CS2, Dota 2 и FACEIT Anti-Cheat;
- уведомления в Telegram;
- отчётность и учёт трудозатрат.

Все команды разработки, миграции, тесты и сборка должны выполняться через Docker. На хосте достаточно Docker Compose и Git.

## 8. Мониторинг

Предусмотри приём:
- температуры CPU и GPU;
- нагрузки CPU и GPU;
- использования RAM;
- свободного места;
- heartbeat и времени последней связи.

Для MVP реализуй:
1. Версионированный API приёма.
2. Регистрацию агентов.
3. Небольшой Python-агент для Windows.
4. Симулятор для локальной проверки без доступа к клубу.

Агент должен иметь собственный идентификатор и отзываемый токен. Токен ограничен конкретным агентом и разрешёнными устройствами. Не доверяй club_id из тела запроса.

Для общего образа CCBoot не допускай клонирования одной регистрации на все ПК. Опиши безопасное первичное подключение и повторную регистрацию.

Если источник температур не доступен, отправляй null со статусом причины. Не подставляй вымышленные значения и не обещай получение всех датчиков на любом оборудовании.

Проверь доступные способы чтения датчиков. Используй документированный источник и явно укажи зависимости. Не устанавливай неподтверждённые драйверы автоматически.

Добавь:
- настраиваемые пороги;
- выдержку времени перед тревогой;
- отдельный порог восстановления;
- защиту от повторных уведомлений;
- интервалы технического обслуживания;
- различие между отсутствием связи, отсутствием датчика и измеренным нулём.

Без внешнего подтверждения не называй отсутствие heartbeat доказательством выключения ПК.

Не реализуй удалённое выполнение произвольных команд, перезагрузки и автоматическое изменение образов.

## 9. Обновления игр и FACEIT

Отслеживай:
- CS2, Steam AppID 730;
- Dota 2, Steam AppID 570;
- FACEIT Anti-Cheat.

Разделяй события:
1. Изменилась опубликованная версия.
2. Изменилась локально установленная версия.
3. Работоспособность подтверждена проверкой специалиста.

Эти события не должны подменять друг друга.

### Steam

Используй интерфейс провайдера сведений о версиях, чтобы источник можно было заменить.

Допускается сторонний steamcmd.net после проверки формата и условий использования. Явно обозначь его как сторонний источник.

Проверяй опубликованные версии централизованно один раз для каждой игры, затем распределяй события по подписанным клубам. Не опрашивай один источник отдельно для каждого ПК.

Храни:
- источник;
- ветку;
- build ID;
- время проверки;
- время публикации, если доступно;
- состояние источника и свежесть данных.

Смена build ID может быть откатом. Показывай старое и новое значение без неподтверждённого вывода о характере изменения.

Локальные версии получай от агента через Steam manifest-файлы, если они реально поддерживаются установленным способом обновления. Если iCafeCloud их не ведёт, показывай ограничение.

### FACEIT

Не выдумывай публичный API версии античита.

Исследуй доступные официальные источники. Если надёжного источника релиза нет:
- отобрази это ограничение;
- реализуй контроль версии или хеша выбранного локального файла;
- называй событие «изменился контролируемый файл»;
- не представляй его как подтверждённый релиз или успешное обновление всех компонентов.

Не сканируй и не изменяй образы CCBoot автоматически.

При первом подключении сохраняй исходное состояние. Не отправляй его как новое обновление. Для нестабильных источников используй подтверждение последовательными проверками.

## 10. Telegram

Настройка через интерфейс:
- токен бота;
- chat_id;
- тестовое сообщение;
- подписки на клубы и типы событий.

Секреты шифруй при хранении и скрывай при повторном отображении. Не включай токены в логи и тексты ошибок.

Типы уведомлений:
- опубликованная сборка игры изменилась;
- локальная сборка изменилась;
- изменился файл FACEIT;
- мониторинг обнаружил проблему;
- проблема устранена;
- критическая заявка;
- приближается или просрочен осмотр;
- источник обновлений длительно недоступен.

Уведомления отправляй через очередь. Реализуй transactional outbox или другой обоснованный способ не терять события между транзакцией БД и постановкой задания.

Нужны:
- дедупликация;
- идемпотентная обработка;
- retry с backoff;
- обработка HTTP 429 и retry_after;
- журнал попыток;
- failed jobs и ручной повтор.

Не обещай exactly-once доставку во внешний Telegram API: предусмотрительно обработай ситуацию, когда сообщение принято, но ответ потерян.

Не отправляй реальные сообщения во время автоматических тестов. Используй fake transport.

## 11. PostgreSQL и производительность

Проектируй под рост, но не заявляй производительность без измерений.

Используй:
- миграции и внешние ключи;
- unique и check constraints;
- индексы под реальные запросы;
- составные индексы с учётом клуба, статуса и времени;
- транзакции;
- защиту от конкурентного изменения статусов;
- eager loading и устранение N+1;
- серверную пагинацию;
- пакетную запись телеметрии.

Не храни всё в JSONB. Основные поля и связи должны быть типизированы; JSONB используй для действительно расширяемых данных.

Деньги храни как integer в минимальных единицах с валютой либо как numeric. Не используй float.

Время событий храни в timestamptz и UTC, отображай в часовом поясе клуба. Для календарных сроков используй подходящую модель дат.

Телеметрию отдели от заявок и оборудования:
- ограниченная политика хранения сырых измерений;
- агрегаты для графиков;
- индексы по устройству и времени;
- пакетная очистка;
- отсутствие бесконечного роста.

Оцени партиционирование по времени на измерениях. Если вводишь его сразу, реализуй создание будущих партиций и удаление истёкших, а не только DDL одной таблицы.

Подготовь нагрузочный сценарий на условные 100 клубов по 100 ПК с heartbeat раз в минуту:
10 000 / 60 ≈ 167 сообщений в секунду в среднем.

Это целевая модель нагрузки, а не доказанная мощность приложения. Добавь jitter, чтобы агенты не отправляли данные одновременно.

Для ключевых запросов покажи EXPLAIN ANALYZE на синтетических данных. Нагрузочные тесты выполняй только в отдельном тестовом окружении.

Зафиксируй:
- конфигурацию машины;
- объём данных;
- пропускную способность;
- p50, p95 и p99;
- ошибки;
- задержку очередей;
- найденные ограничения.

Не объявляй приложение готовым к целевой нагрузке, если такой тест не выполнен.

## 16. Тесты и критерии приёмки

Проверь автоматически:
- изоляцию данных между клубами, включая вложения и API;
- роли и разрешённые переходы заявок;
- запрет закрытия заявки без результата;
- даты осмотра, включая конец месяца;
- сохранение пропущенных устройств;
- отзыв токена агента;
- повторную отправку одного пакета телеметрии;
- отсутствие ложного нуля при отсутствии датчика;
- пороги тревог и восстановление;
- дедупликацию событий обновления;
- таймаут и недоступность источника;
- Telegram 429 и сбой отправки;
- повторное выполнение задания;
- конкурентные изменения.

Проверь E2E:
создать клуб → добавить ПК → создать заявку → назначить специалиста → выполнить работу → закрыть заявку → увидеть историю.

Второй E2E:
принять телеметрию → подтвердить превышение порога → создать событие → поставить уведомление → зафиксировать результат доставки через тестовый транспорт.

Третий E2E:
обнаружить смену опубликованной сборки → создать одно событие → уведомить подписанные клубы → принять локальную версию → отдельно отметить проверку работоспособности.

MVP принимается, когда:
- разворачивается с чистого checkout по README;
- запускается через Docker Compose;
- миграции проходят на чистой БД;
- основные сценарии работают через интерфейс;
- тесты и frontend-сборка проходят;
- очереди и scheduler работают;
- данные сохраняются после перезапуска контейнеров;
- есть проверка восстановления резервной копии;
- ограничения интеграций честно отображены.
